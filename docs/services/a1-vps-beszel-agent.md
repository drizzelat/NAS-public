# Service: A1 Beszel agent

## Overview

Beszel agent on the **Ampere A1 Matrix host** (`a1-matrix`, arm64). Reports the A1 to
the Beszel hub on the NAS so it shows up in the dashboard at
`https://beszel.example.com` alongside the NAS and the AMD micro. Host metrics:
CPU / memory / **root-disk** / network / temp, plus **per-container Docker metrics**
via a GET-only socket-proxy (see below). Same design as the [micro VPS agent](micro-vps-beszel-agent.md);
this doc only calls out where the A1 differs.

The A1 is public and the hub is on the CGNAT'd NAS, so this agent uses the
**WebSocket** connection model — it dials **out** to the hub — instead of the
classic hub→agent dial-in the [NAS agent](beszel.md) uses.

## Stack

- **Stack folder:** `stacks/a1-vps-beszel-agent/`
- **Compose file:** `stacks/a1-vps-beszel-agent/docker-compose.yml`

- **Runs on:** the Ampere A1 ([host + SSH details](a1-vps-matrix.md)).

## Connection (WebSocket, outbound)

| Setting   | Value                          | Why |
| --------- | ------------------------------ | --- |
| `HUB_URL` | `http://100.64.0.11:8090`   | Hub over Tailscale — direct, no Caddy loop, no TLS |
| `LISTEN`  | `127.0.0.1:45876`              | Legacy SSH-tunnel listener pinned to loopback — nothing on the public IP |
| `SYSTEM_NAME` | `a1-matrix`                | Matches the tailnet peer name |
| `KEY`     | Komodo Variable from the vault (per-system) | Public key the hub shows when adding the system |
| `TOKEN`   | Komodo Variable from the vault (per-system) | Authenticates the WebSocket connection |

Outbound-only means **no inbound port, no Oracle-iptables rule, nothing bound on the
public IP `198.51.100.20`**. The agent reaches the hub over the tailnet (peer `nas`).

> **Tailnet ACL is required (this bit us on first deploy).** The A1 is a **tagged**
> node (`tag:a1-matrix`); the NAS is a user-owned, untagged device. Tagged nodes get
> **no** default access to user devices, so data traffic a1→nas is dropped by the ACL
> even though the tunnel is up — the agent logs `WebSocket connection failed … i/o
> timeout`. Diagnostic tell: `sudo tailscale ping 100.64.0.11` **succeeds** (disco
> handshake is at the WireGuard layer, ignores the ACL) while `curl http://100.64.0.11:8090`
> **times out**. Fix in the Tailscale admin console — grant `tag:a1-matrix` → hub:
>
> ```json
> { "action": "accept", "src": ["tag:a1-matrix"], "dst": ["100.64.0.11:8090"] }
> ```
>
> The nightly A1 backups run the other way (the NAS pulls from the A1), so they need no
> wider grant. The agent reconnects on its own once the
> ACL is saved — no redeploy. The micro agent never needed this because the micro is a
> user-owned node, not gated by a tag.

## Environment variables

From the vault (`secrets.enc/portainer-env/a1-vps-beszel-agent.env.age`), written into the Komodo
Variables `A1_VPS_BESZEL_AGENT__*` by `scripts/secrets.sh push a1-vps-beszel-agent`, which then
deploys through Komodo. Never committed in the clear. Until 2026-09-15 the vault's token was not
the one the agent ran with; at adoption the vault took the live value (komodo-migration.md F20).

| Variable                | Description                                        |
| ----------------------- | -------------------------------------------------- |
| `BESZEL_VPS_AGENT_KEY`   | `KEY` — public key from the hub                    |
| `BESZEL_VPS_AGENT_TOKEN` | `TOKEN` — WebSocket auth token                     |

Both are generated by the hub when you **Add System**. The names are the same as the micro agent's
(the compose file is a copy); the values are the A1's own.

## Disk monitoring (root fs + block volume, no host `/` exposure)

Same trick as the micro: an **empty probe dir** bind-mounted to
`/extra-filesystems/<name>:ro`. `statfs` of any path returns that whole filesystem's
usage, so this reports real disk numbers with **zero file exposure** and without
handing the agent `/etc/shadow`. Two filesystems on the A1, so two probes:

| Probe dir (host) | Mount | Hub name | Filesystem |
| --- | --- | --- | --- |
| `/var/lib/beszel-root-probe` | `/extra-filesystems/root:ro` | `root` | 45 GB root fs |
| `/opt/matrix/beszel-probe` | `/extra-filesystems/matrix:ro` | `matrix` | 100 GB block volume (Matrix data) |

Both probe dirs are Docker-auto-created empty and root-owned; each just has to sit on
the filesystem it measures.

## Docker metrics via GET-only socket-proxy

`network_mode: host` is kept for real host network-interface stats. Per-container
metrics come through the `beszel-socket-proxy` sidecar (`tecnativa/docker-socket-proxy`,
same as `stacks/beszel/`), **not** a raw `/var/run/docker.sock` mount — a `:ro` socket
bind on a host-net container still lets the daemon API accept `POST` (= host root).
The proxy is GET-only (`CONTAINERS`/`PING`/`VERSION`, `POST: 0`) and binds host
loopback `127.0.0.1:42375`; the agent reads container stats via
`DOCKER_HOST=tcp://127.0.0.1:42375` with zero write surface on the daemon. The proxy
image is a multi-arch manifest index, so the same digest resolves on this arm64 host.

## First-time setup

1. **Hub UI → Add System.** In `https://beszel.example.com`, **Add System**, choose
   the **WebSocket** connection. The hub emits a **KEY** and **TOKEN**.
2. **Create the env secret.** Add `BESZEL_VPS_AGENT_KEY` / `BESZEL_VPS_AGENT_TOKEN` to the vault:
   `./scripts/secrets.sh edit a1-vps-beszel-agent` (edits the plaintext, then locks).
3. **Push, then create the stack from your workstation.** *(This step is the original Portainer
   bring-up. Since 2026-09-15 a rebuild writes the Variables with
   `scripts/secrets.sh komodo-vars a1-vps-beszel-agent` and deploys from Komodo.)* Commit `stacks/a1-vps-beszel-agent/`
   together with the new `secrets.enc/portainer-env/a1-vps-beszel-agent.env.age` and push.
   `deploy-stacks` stops at this stack with `is NEW and its env lives in the vault` — expected,
   CI holds no vault key. Then `./scripts/secrets.sh push a1-vps-beszel-agent` creates the stack
   from `main` with its env, routed to endpoint 5 by the `a1-vps-` prefix, and
   `gh workflow run deploy-stacks.yml -f stacks=a1-vps-beszel-agent` health-checks it.
4. **Grant the tailnet ACL.** The A1 is a tagged node, so add the `tag:a1-matrix` →
   hub grant in the Tailscale admin console (see the Connection note above). Without it
   the agent logs `i/o timeout` forever.
5. **Confirm online.** The A1 system flips to *online* once the agent connects out over
   the tailnet. If not, check KEY/TOKEN match exactly (a stray space fails auth) and
   that the A1 can reach `100.64.0.11:8090` (`curl` it from the A1; `sudo tailscale
   status` shows peer `nas`).
6. **Thresholds / alerts** — set per-system CPU/mem/disk thresholds; alerts route like
   the NAS ([beszel.md](beszel.md)).

## Operations

> Redeploy is a **git push** to `stacks/a1-vps-beszel-agent/` (the runner deploys it through
> Komodo), or **Deploy** on the Komodo Stack. The A1 `ubuntu` user needs `sudo docker` for
> host-side checks.

### Upgrade

`henrygd/beszel-agent` pinned to a **version tag**`@sha256:…` (see compose; moved off
`latest` so Renovate tracks version bumps, not just the digest). The digest is a
multi-arch index so the same pin resolves on this arm64 host. Keep it in step with the
NAS agent pin in `stacks/beszel/` and the micro's.

### Common failures

- **Agent logs `WebSocket connection failed … i/o timeout`** → tailnet ACL blocks the
  tagged A1 from the NAS. Confirm with `sudo tailscale ping 100.64.0.11` (works) vs
  `curl http://100.64.0.11:8090` (times out); fix = the `tag:a1-matrix` grant (see
  the Connection note). This was the actual first-deploy failure.
- **Hub shows the A1 offline** → agent can't reach the hub. Check
  `sudo tailscale status` on the A1 (peer `nas` online), and that KEY/TOKEN in the
  vault (and so the Komodo Variables) match the hub's values exactly.
- **`docker pull` fails on the A1** → tailscale MagicDNS hijacked system DNS. Fix:
  `sudo tailscale set --accept-dns=false` (same as the Matrix stack).
